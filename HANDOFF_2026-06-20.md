### FFA bug-fix batch (v5.1.270) — Sam: "work on the Free For All, it's still buggy"
Three real bugs, found by running a full 6-player FFA match end-to-end in the harness (start → 600 ticks → `drawBB()`):
- **270 — RENDER CRASH (the big one):** FFA fills the empty grid seats with **synthetic CPUs** bound to binds *past* the configured seats, but `tankGridApply()` sets those binds' `m2.drive = null`. `p2DriveCtx()` did `m2.drive[p].kind` with **no guard**, so `withBot()`→`drawRobot()` threw *"Cannot read properties of null (reading 'kind')"* the instant an FFA match with **any** empty seat tried to draw — i.e. essentially every FFA match (you set up 1–2 humans, the rest fill with CPUs). FIX: `startP2BB` now assigns each filled bind a real drive (**random**, for drivetrain variety) + a sens; `p2DriveCtx` defaults to field-centric swerve if a drive is ever missing (defense-in-depth).
- **270 — INVISIBLE HUD (4 of 6 bots had no HP bar):** the in-match status-panel loop used `row=[0,0]` + `(b.side===0?left:right)` — a **2-side** layout. Each FFA bot is its OWN side (0–5), so side 0 went left, side 1 right, and sides 2–5 indexed `row[2..5]` (undefined) → `r=NaN` → `y=NaN` (drawn off-canvas). New **`bbHudSlot(p)`**: 2-side hugs each side's edge (regression-safe), FFA splits all N factions into a LEFT/RIGHT column (3+3) so all six show their HP/mobility.
- **270 — DUPLICATE BINDS:** FFA built its roster via `tankRosterFromSeats()`, which auto-fills an empty *side* with a `bind:0` CPU — in FFA that **collided with seat 0** (two bots sharing one bind → same drive/input); the fill loop's `bind:base.length` also collided for non-contiguous seats. FIX: FFA now builds straight from the **ready seats** (real seat index = a unique bind) and fills the rest with the **next unused bind**.
- smoke57 **+10 asserts → 554 pass**: 5 `bbHudSlot` (FFA 6 finite slots / 2 columns / no overlap + 2-side regression) and a 5-assert **FFA integration test** (real match starts 6-bot, every bind has a drive, all binds distinct, seat 0 is the human, `drawBB()` renders without throwing).

### STORY-MODE soft-lock fix (v5.1.273) — Sam: "a lot of soft locks and game-breaking bugs in story mode"
**The big one.** Nearly every career stage is reached through a coach lesson: `goto:'coach:CX', then:'stage:YY'`. The `then` was stored only in the transient `career._then`, while `career.node` rested on the **coach beat** for the whole match. So if the player **ESC'd out of the match** (`p2Back` → `p2cbeat`, line ~7312) — or ESC'd the coach beat → hub → CONTINUE — `_then` was already consumed → the coach's "Got it" fell through to the hub → hub CONTINUE re-entered the same coach with no `then` → a **coach↔hub loop**. The stage was unreachable; only a progress-wiping "NEW JOURNEY" escaped. Because almost every stage sits behind a coach lesson, it felt like "a lot of soft locks."
- **FIX:** `careerGoto` now persists each beat's continuation keyed by node — `career._thenByNode[ref] = thenRef` — and `careerContinue` falls back to it (`career._then || career._thenByNode[career.node]`). A coach beat can always recover its stage even after `_then` is gone.
- **Defense-in-depth:** `startCareerMatch` on a missing stage id bails to the hub (was a silent no-phase-change freeze); a quiz whose topic has no questions for the lane **skips** to its `next` instead of crashing `drawCareerQuiz` (`q = Q.qs[0] = undefined`); a finale beat's "Finish" routes to the **recap**, not the hub.
- **How it was found / verified (reusable):** a headless **Playwright** harness drives career via the real click/nav functions. (1) An in-page **graph-integrity check** over `CAREER_BEATS`/`CAREER_STAGES` (no missing goto/then/next/after targets, no empty quiz pools — all clean). (2) A **logic fuzzer**: 900 randomized playthroughs across all 4 lanes that inject **ESC at matches and beats** + force win/loss/draw — caught the loop, and after the fix reports **0 soft-locks / 0 crashes / 0 stucks**, every run reaches an ending. (3) A **render fuzzer**: draws every beat × lane × lastResult × chem, every quiz state, every recap ending × finale result, the hub — **0 throws**. Scripts live in the scratchpad (`career_check.js` / `career_fuzz2.js` / `career_render.js`).

## ⚠️ Gotchas (learned this thread)
- The HTML build has **very long base64 lines** (`_logoMain`/`_logoIG`/etc.). `Read` on a large offset can error with "content exceeds tokens" — use **Grep with context** or `Read` a small line range instead, and edit via unique strings.
- **smoke57's test body is an eval'd template string** — an apostrophe inside an `ok('…')` label (even written as `\'`) breaks it with "missing ) after argument list". Avoid apostrophes in those labels.
- `battery.sh` exit code is trustworthy **only after** `extract.sh`.
- **The harness canvas is a no-op mock**, so a bug that only throws in the *real browser render* (like the v5.1.270 FFA null-drive crash) won't show up unless a test actually **calls the draw function** (`drawBB()`) on a realistic match. The new FFA integration test in `smoke57.js` does exactly this — copy that pattern (it reuses smoke57's stub block) to catch render crashes in other modes.
- **FFA roster math is fiddly:** each bot is its own `side` (0–5) **and** needs a unique `bind` (→ `m2.drive[bind]`/`playerBind[bind]`/input). `tankRosterFromSeats()` is built for the 2-side path and auto-fills an empty side with a `bind:0` CPU — don't route FFA through it; build straight from `m2.tseats` ready seats. Any new per-bot HUD/render code must not assume 2 sides (`[0,0]`/`side===0`).
- When you add a gallery tile type, update the count asserts in `smoke52.js` AND `smoke57.js`.
- Screenshots: a headless Playwright/Chromium is available (`/opt/pw-browsers`); the `/tmp/shotcr.js` pattern this thread used loads the HTML, waits for `CW`/a fn, and screenshots the canvas.
